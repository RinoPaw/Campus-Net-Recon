# 05-Win7 有线接入网络、默认网关与跨域回程观察

> 观察日期：2026-11-06。设备：个人 Windows 7 SP1 有线主机（通过 Reinor 只读远程命令）、自有 OpenWrt 宿舍路由器。**确认：Win7 的默认网关是 `192.168.236.254`；`10.203.255.254` 是宿舍 OpenWrt 的校园网上游网关；`10.202.255.254` 是宿舍 OpenWrt 自身的上联地址。** Win7 与宿舍路由器所在地址段之间存在方向性可达性差异，尚未确认 NAT 位置、VLAN ID 以及 Win7 的 ICMP 应答者是否为本机 OpenWrt。

> **后续修正（2026-11-06）：** 新的 OpenWrt 同步抓包未能证明 Win7 的 Echo Request 到达该路由器。此处保留当时的路由、Ping 和逆向路径观察，但不得继续将 `10.202.255.254` 的 ICMP 回复直接归属为宿舍 OpenWrt。参见 [第 10 篇](10-校园网有线无线公网出口与NAT路径观察.md)。

## 5.1 背景与前期文献

延续 [01-奇怪的子网掩码](01-奇怪的子网掩码.md) 和 [02-锐捷网关的幻术](02-锐捷网关的幻术.md)：早期在宿舍校园 Wi-Fi 观察到 `10.202.0.0/15`、网关 `10.203.255.254`；在教室 Wi-Fi 观察到 `10.201.0.0/16`、网关 `10.201.255.254`。这些是**特定位置、特定时间的客户端网络配置**，不能直接套用到本次 Win7 有线主机。

本次首先检查 Win7 的 IP 配置、路由表和 ARP，随后针对已知设备与已观察到的下一跳做定点 ICMP、tracert 和 DNS 测试。未做网段扫描、口令尝试、配置修改或对第三方终端探测。公开记录仅保留解释拓扑必需的地址，MAC 仅公开 OUI。

## 5.3 Win7 发起的 ICMP 与逐跳路径

2026-11-06 单次短采样，非长期 SLA 数据：

| Win7 目标 | Ping（样本） | 回复 TTL | tracert 位置 |
| --- | --- | --- | --- |
| `192.168.236.254` | 3/3，0–1 ms | 255 | 第 1 跳，直接网关 |
| `192.168.229.253` | 3/3，<1 ms | 63 | 第 2 跳 |
| `49.122.23.254` | 3/3，1 ms | 62 | 第 3 跳 |
| `10.203.255.254` | 4/4，<1 ms | 59 | 第 6 跳 |
| `10.202.255.254` | 6/6，1–2 ms | 58 | 第 7 跳 |
| `1.1.1.1` | 曾收到 Echo 回复 | 61 | 第 4 跳（当次追踪） |

**Win7 → 校园网地址的代表性追踪**（只整理目标为路由设备的已观察结果）：

```text
Win7 192.168.236.49
  hop 1: * * *             [本地默认网关为 192.168.236.254]
  hop 2: 192.168.229.253
  hop 3: 49.122.23.254
  hop 4: 10.0.2.97
  hop 5: 10.0.4.2
  hop 6: 10.203.255.254     [宿舍路由器所用校园网上游网关]
  hop 6: 10.199.1.2         [仅在前往宿舍路由器的追踪中观察到]
  hop 7: 10.202.255.254     [与宿舍 OpenWrt 上联配置相同的目标地址；应答者身份待核实]
```

上面的两条第 6 跳属于**不同目的地址的追踪**，不能视作同一条路径连续出现两次。对于 `10.201.255.254`、`10.205.255.254`、`10.206.255.254`、`10.207.255.254`，也分别在第 6 跳观察到目标响应。

针对第一跳，`ping 192.168.236.254` 正常，然而向第二跳/宿舍路由器发送 TTL=1 的 Echo Request 没有收到 Time Exceeded；`tracert` 因此显示第一跳 `* * *`。不能据此断言实际第一跳缺失或进行了透明二层转发。TTL=255、63、62、59、58 还受到各目标设备初始 TTL 设置影响，不能简单把不同目标的回复 TTL 相减来推导完整路径。

对目标地址 `10.202.255.254` 执行 `ping -f -l 1472`（Windows IPv4、禁止分片）得到 2/2 成功，说明当次往返测试未遇到小于 1500 字节的有效路径 MTU 瓶颈。没有做双向带宽测试。

## 5.4 对照宿舍 OpenWrt：路径方向不对称

在自有 OpenWrt 读取了：

```text
phy-sta1   10.202.255.254/13
br-lan     172.27.207.1/24
campuswg   172.28.207.1/24
default via 10.203.255.254 dev phy-sta1
10.200.0.0/13 dev phy-sta1
ip route get 192.168.236.49
  => via 10.203.255.254 dev phy-sta1 src 10.202.255.254
```

在 OpenWrt 上对 Win7 `192.168.236.49` 连续 Ping，3/3 超时；对 Win7 默认网关 `192.168.236.254` 与其上游 `192.168.229.253` 各 2/2 超时。相反，Win7 对地址 `10.202.255.254` Ping 成功（不能仅凭回复确认就是所管理的 OpenWrt 响应）。

**关键证据**：OpenWrt 对 `192.168.236.49` 的反向 `traceroute` 从 `10.200.1.5` 出发，后续可观察到 `111.5.x.x`、`221.183.x.x` 等公网运营商路由节点，而未抵达 Win7。这与 Win7 → 目标地址 `10.202.255.254` 经过校内 `49.122.23.x`、`10.0.x.x` 的前向路径不同。

合理假设包括：Win7 发往宿舍路由器的报文在中途经过了源地址转换（SNAT）；两端处于不同的 VRF / 路由策略域；或者 `192.168.236.0/24` 缺乏从宿舍网络方向可用的返回路由，并伴随访问控制。**现有数据不能排除或单独证实任何一种解释**。尤其不能仅凭 Win7 → OpenWrt 的 Ping 成功，推断 OpenWrt 能直接回访 Win7 的私网地址。

上联邻居表的一个脱敏统计：47 个 IPv4 邻居项，46 项指向相同 MAC，另 1 项不同。这与既有 [02](02-锐捷网关的幻术.md) 中的 Proxy ARP 观察相符，但邻居缓存和代理 ARP 的最终归属仍需在接入设备侧确认；未公开第三方 IP 或完整 MAC。

## 5.5 网关地址与区域关系

从 Win7 对 `10.200.255.254` 至 `10.216.255.254` 共 17 个特定地址的单次 Echo 采样：`10.201`、`10.202`、`10.203`、`10.205`、`10.206`、`10.207` 的 `.255.254` 回复；其余本次未回复。可达不等于属于当前本地网段，也不意味着它是本机网关。这个采样与早期校园 Wi-Fi 在 `10.20x` 上观察到的区域网关习惯部分一致。

`49.122.23.254` 属于 `49.122.16.0/21`，公开网络注册信息关联中国教育和科研计算机网（CERNET / AS4538），见 [该地址范围登记信息](https://www.bigdatacloud.com/network-lookup/49.122.16.0/20)。这一线索支持教育网转发路径的归属判断，但不能定位某台物理交换机。

## 5.6 DNS 与接入策略旁证

- `nslookup xuhuaai.top` 使用本机 `114.114.114.114`，正常返回自有服务器地址。
- `nslookup xuhuaai.top 223.5.5.5` 也成功；`223.5.5.5` 的短 Ping 样本约 16–18 ms。
- `nslookup www.example.com 1.1.1.1` 在本次测试中超时；`114.114.114.114` 可查询。这只说明当次特定 DNS 查询未响应，不能归结为永久封锁。
- OpenWrt 上联 DNS 为 `223.5.5.5`，与 Win7 静态 DNS 设置不同。
- Win7 没有 IPv6 默认路由，故本次追踪均按 IPv4 分析。

## 5.7 已证实 / 待证实

**已证实**：Win7 本地 `192.168.236.0/24`，静态地址、默认网关 `192.168.236.254`；本地网关 ARP 可解析；上游路径前两段分别经 `192.168.229.253` 和 `49.122.23.254`；Win7 → `10.202.255.254` 有 Echo Reply，尚未确认应答实体；反向 ICMP 和反向追踪没有找到相同的路径；宿舍 OpenWrt 的上联为 `10.202.255.254/13`，默认路由指向 `10.203.255.254`。

**未证实**：Win7 所接交换端口的 VLAN 编号、`192.168.236.254` 的确切硬件型号、`192.168.229.253` 是交换路由器还是其他服务网关、Win7 出站流量是否 SNAT、SNAT 的具体位置、上游是否采用 VRF / PBR，以及不同位置/认证状态是否会重写路由策略。

## 5.8 后续有判别力的最小实验

1. **后续实测已经执行定向抓包。** Win7 对 `10.202.255.254` 收到应答，而 OpenWrt 的 `phy-sta1` 未观察到与 Win7 同期定长 Echo Request 相匹配的报文。详细见 [第 10 篇校园网出口与 ICMP 应答者验证](10-校园网有线无线公网出口与NAT路径观察.md)；须重新确认应答设备身份后才能推断 NAT 位置。
2. 仅由自有 Win7 复测本网关、第二跳和宿舍 OpenWrt 的 `tracert` / `ping`，在不同时间采样，以排除一次性路由变化。
3. 如有网络管理员提供的交换机/AC 资料，再核对 Win7 物理端口所属 VLAN、三层 SVI、DHCP 地址池与有线认证模式。
4. 检查自有 OpenWrt 的最小范围路由/策略记录，解释为何 `192.168.236.0/24` 的反向流量进入运营商路径。

**研究边界**：不更改校园网 DHCP/ARP、认证状态，不猜测第三方终端身份，不执行大范围发现扫描或未经许可的交换设备配置探查。结论都基于本次观察，不外推到整个校园网。
