# 14-Win7 第三接入点：公共 DNS 异常、备用 DNS 与公网出口复核

> **观察日期：2026-11-13，约 09:22–09:30（UTC+08:00）**。在个人/获授权的 Windows 7 SP1 32 位有线终端（本文匿名别名 `win7-3`）及自有腾讯云主机 `rino-tx` 上进行**少量定向、只读网络测试**；并查询自有 Nginx 日志。没有修改校园网或测试终端的网络设置。该实验补充 [12](12-Win7第三接入点245网段观察.md) 与 [13](13-跨网段公网IP异常路径对照.md)。

## 14.1 研究目的与环境

[11](11-Win7第二接入点243网段观察.md)、[12](12-Win7第三接入点245网段观察.md) 已发现两个不同校园网私网子网对 `1.1.1.1` 与 `1.1.1.2` 返回异常低 RTT 和特殊 TTL。为减少「公共服务本身故障」和「本机 DNS 设置」等混杂因素，这次将**同一组 IP、同一种 DNS 请求**分别从校园 Win7 与自有云服务器发出，同时检测实际公网出口。

| 条件 | 校园 Win7 | 自有云服务器 |
| --- | --- | --- |
| IPv4 | `192.168.245.38/24` | 公网主机，内部云网卡接口 |
| 默认网关 | `192.168.245.254` | 云服务商网络，路由独立于校园 |
| Win7 DNS | `114.114.114.114` 与 `10.3.0.3` | 本次 UDP 查询均直接指定目的 IP |
| 代理 | WinHTTP 显示直连；UDP 为原生 Socket | 原生 UDP Socket |
| 时间 | 同日短时样本，非长期连续观测 | 同日短时样本 |

## 14.2 两端对同一组目标的 ICMP 对照

客户端在同一轮中对四个目标各发 2 次 Echo (`ping -n 2 -w 450`)；腾讯云对应执行 `ping -c 2 -W 1`：

| 目的 IP | Win7 实测 RTT | Win7 回复 TTL | 腾讯云 RTT | 腾讯云回复 TTL |
| --- | --- | ---: | --- | ---: |
| `1.1.1.1` | 两次均低于 1 ms | 61 | 81.9、111 ms | 251 |
| `1.1.1.2` | 两次均低于 1 ms | 250 | 92.4、93.0 ms | 251 |
| `1.0.0.1` | 两次均 83 ms | 46 | 80.2、80.9 ms | 251 |
| `1.1.1.3` | 两次均 85 ms | 46 | 两次约 83.1 ms | 251 |

结论仅限于这些样本：**Win7 到前两个地址的应答模式与云主机明显不同，而后两个地址具有相近的往返时延**。Ping 回复 TTL 可以来自不同初始 TTL 和不同返程路径，不可机械换算跳数；也不能据此识别 ICMP 报文真实生成者。

## 14.3 直接构造 UDP DNS 请求：对照结果

在 Win7 PowerShell 2.0 里使用 `.NET System.Net.Sockets.UdpClient`，并在云端用 Python `socket`，均构造标准 DNS 单问题请求：

- Transaction ID：`0x735a`，RD=1，QDCOUNT=1；
- QNAME：`example.com`；QTYPE=`A`；QCLASS=`IN`；
- 直接发送到指定目标 `UDP/53`，不经系统域名解析；
- 云端校验返回事务 ID、RCODE 和 ANCOUNT；Win7 返回了对应的 DNS 格式响应时读取 RCODE、ANCOUNT，但没有在 Win7 脚本里额外断言事务 ID。

| DNS 服务器 | Win7 原始 UDP 请求 | 云端原始 UDP 请求 |
| --- | --- | --- |
| `1.1.1.1` | `SocketException: ConnectionReset`，约 3 ms | 正常响应，92 ms，RCODE=0，2 答案 |
| `1.1.1.2` | `SocketException: ConnectionReset`，约 3 ms | 正常响应，87 ms，RCODE=0，2 答案 |
| `1.0.0.1` | 正常响应，约 93 ms，2 答案 | 正常响应，86 ms，2 答案 |
| `114.114.114.114` | 正常响应，2 答案 | 正常响应，23 ms，2 答案 |
| `223.5.5.5` | 正常响应，约 21 ms，2 答案 | 正常响应，3 ms，2 答案 |
| `10.3.0.3` | `SocketException: TimedOut`；独立 Ping 0/2 | 未测（非公网服务） |

Windows 已对特定目标 `UdpClient.Connect` 后发出 UDP 请求，`ConnectionReset` **通常表示操作系统从网络栈收到 ICMP 端口不可达类错误**；它不证明 UDP DNS 服务器自身生成了错误，也无法判断是校园网哪一个节点发出的。与云端相同报文成功、Win7 对 `1.0.0.1` 成功的对照一起，显著加强了「校园网路径上存在针对前两地址的特殊转发/应答/过滤行为」这一解释。**当前还不能断言具体设备、规则或是否存在地址劫持。**

## 14.4 TCP 53/80/443 连接：时间差异

使用 Win7 `TcpClient.BeginConnect`，每个目标约 900 ms 等待窗口，同时报告 Socket 结果。新一轮观察：

- `1.1.1.1:53/80/443`：超时；
- `1.1.1.2:53/443`：超时；
- `1.0.0.1:53`：可建立 TCP（约 79 ms），`443`：超时；
- `10.3.0.3:53`：超时；
- `114.114.114.114:53`：可连接（约 25 ms）。

**与 2026-11-13 较早一次测试不同**：早前对 `1.1.1.1`、`1.1.1.2` 的 TCP 53/443 曾报告「ConnectionRefused」；本轮在约 900 ms 等待窗口内未收到可完成连接的应答，记录为超时。两轮测试使用的调用方式/超时时长可能不同，尚无证据证明是网络设备动态切换策略，不能把单次差异当成确定机制。

腾讯云对上述几个公共 DNS IP 的 TCP/53 均可完成连接（短时检查）；而对 443 的基础短时连接在云端也有失败/超时，不据此作校园网特有的 HTTPS 判断。

## 14.5 备用 DNS `10.3.0.3`：路径存在，但服务未响应

`10.3.0.3` 是 Win7 静态配置的第二个 DNS 服务器（前一篇已通过 `ipconfig /all` 和 WMI 验证）。它本次表现：

- Win7 `ping -n 2 -w 500`：0/2 收到 Echo Reply；
- 直接 `UDP/53` 标准请求：接收超时；
- 直接 `TCP/53`：连接超时（约 900 ms）；
- `tracert -d -h 12 -w 125`：可见如下中间地址，第 8–12 跳没有回应：

```text
1  * * *               （本地 192.168.245.254 能单独 Ping 通）
2  192.168.229.253
3  49.122.23.254
4  10.0.2.97
5  10.0.4.2
6  10.0.4.6
7  10.0.4.18
8–12  * * *
```

可确定该目的地址至少沿某条校园上游路径转发至一系列中间路由器；之后没有收到正常服务应答。**不能认定 `10.3.0.3` 已停机**，也可能有返回路由、源地址可见性、防火墙或 DNS 服务 ACL 限制。此次未读取或改变校园 DNS 服务器配置。

## 14.6 到自有腾讯云：出口确认和完整路径对照

为避免只凭路由追踪推断 NAT 出口，在 Win7 用原生 TCP Socket 连接自有云服务 `62.234.68.123:80`，发出唯一标识的 HTTP GET 请求，并在自有 Nginx 的访问日志中找到同一标识：

- Win7 本机 Socket 地址为 `192.168.245.38`；
- 云端收到 HTTP/1.1 请求，返回 `301 Moved Permanently`（合法的 HTTP → HTTPS 重定向）；
- Nginx 记录的真实来源为 **`171.15.162.x`**（完整地址只在用户自有服务器的日志中保存），属于先前识别的河南电信出口地址系列。

`tracert -d -h 10 -w 130 62.234.68.123` 同期看到：

```text
1   * * *             (本地网关 192.168.245.254)
2   192.168.229.253
3   49.122.23.254
4   10.0.2.97
5   10.0.4.2
6   10.199.1.2
7   10.200.1.14
8   171.15.162.1
9   222.85.12.29 (部分探测回应)
10  * * *
```

这一可见前缀与 [04](04-流量路径与边界验证.md) 中第一台 Win7 `192.168.236.49/24` 到同一自有云服务器的逐跳记录**逐项吻合**。结合服务器实际看到的公网来源，支持「`236` 和 `245` 两个有线子网共用可见电信出口路径」的结论；**仍不能由此确定 NAT 位于 `10.200.1.14`，或两个源子网共用同一物理设备、同一条后续完整路径**。

## 14.7 综合判断与研究边界

| 判断 | 当前证据强度 |
| --- | --- |
| `win7-3` 对 `1.1.1.1/1.1.1.2` 的 ICMP 和 UDP DNS 行为异于独立云端 | **较强**：同期两端目标对照、相同 DNS 查询成功/失败 |
| 异常存在于多个 Win7 有线接入子网 | **较强**：见 [11](11-Win7第二接入点243网段观察.md)、[12](12-Win7第三接入点245网段观察.md) |
| `236` 与 `245` 子网共用已观察到的出口路径及运营商地址范围 | **较强**：逐跳路径吻合 + 自有 Nginx 日志 |
| `10.3.0.3` 当前从 `win7-3` 可正常提供 DNS | **不支持**：ICMP、TCP/53、UDP/53 均未获得正常应答 |
| `1.1.1.1` 的 Ping 或 DNS 错误一定由哪台上游路由器生成 | **未知**：未进行链路层抓包或获得运营设备日志 |
| DNS 拒绝/超时是否受认证状态、区域、具体时间影响 | **未知**：缺少严格控制变量的长期/多时段样本 |

下次若继续，应优先获得**经授权的上游运维路由/ACL 证据**或在自有/受控链路上进行报文验证；单纯增加重复 Ping 数量难以判断 ICMP 报文应答者。保持对第三方设备的最小接触，不修改校园 DNS、网关、认证或访问控制设置。
