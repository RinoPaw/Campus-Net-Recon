# 12-Win7 第三接入点：192.168.245.0/24 实测

> 观察日期：**2026-11-13**。第三台个人/获授权 Windows 7 SP1 主机经 Reinor 接入后，执行了只读网络配置、少量 ICMP、traceroute、目标 TCP 连接及 DNS 查询。本文取自同日远程命令实际返回，未修改主机设置。设备以 `win7-3` 匿名表示，完整 MAC、主机名和旁观邻居标识不公开。所在校区、网络认证状态未记录，不做推断。

## 12.1 主机网络环境

| 项目 | 测量值 |
| --- | --- |
| OS / Shell | Windows 7 SP1，32 位；PowerShell 2.0 |
| 物理接口 | Realtek PCIe GBE Family Controller |
| IPv4 / 掩码 | `192.168.245.38/24`（`255.255.255.0`） |
| 默认 IPv4 网关 | `192.168.245.254` |
| 主备 DNS | `114.114.114.114`、`10.3.0.3` |
| DHCP | 关闭，静态地址 |
| IPv6 | 发现链路本地地址；未确认可用 IPv6 默认路径 |
| WinHTTP 代理 | 直接连接 |
| 网关 ARP | OUI `60:0B:03`（H3C 注册前缀），与先前 Win7 接入点一致 |

`route print -4` 显示唯一 IPv4 默认路由为
`0.0.0.0/0 → 192.168.245.254`（本机接口 `192.168.245.38`）。
还存在直连 `192.168.245.0/24`、回环和多播路由，未发现发往校园 `10.x` 地址的独立静态路由。

## 12.2 本地网关与校园内部目标

- `ping -n 2 -w 450 192.168.245.254`：2/2 回复，RTT 低于或约为 1 ms，TTL 255。
- `arp -a`：本地网关以 `60:0B:03` OUI 应答；该 OUI 的登记信息不是设备身份认证。
- 对已在前期研究中观察到的 `192.168.223.254`、`192.168.228.254`、`192.168.235.254`、`192.168.236.254`、`192.168.243.254`、`192.168.245.254` 各执行一次 Ping：本次均收到回复，RTT 小于或约 1 ms、TTL 255。
- `tracert -d -h 4 -w 170 192.168.243.254`：目标在第 1 跳返回。这是观测结果，不能单独证明两个网段在同一二层广播域。
- 对先前已知的两台主机 `192.168.243.77` 和 `192.168.236.49` 各发送一次 Echo Request：两次均无回应。**不等价于跨网段访问被 ACL 阻断**，因为对方是否开机、是否允许 ICMP 均未核验。

对候选校园区域网关 `10.201.255.254`、`10.202.255.254`、`10.203.255.254` 的短时 Ping 均有回应（RTT 低于或约 1 ms），回复 TTL 分别约为 59、58、59。

## 12.3 逐跳路径

使用 `tracert -d`、小范围 `-h 8/9`、`-w 250` 进行定向采样。第一跳在这些 traceroute 中往往显示为 `* * *`，但本机默认网关本身可以正常回应 Ping。

| 跳数 | 到 `1.1.1.1` | 到 `1.1.1.2` | 到 `10.201.255.254` |
| ---: | --- | --- | --- |
| 1 | 无 TTL 过期应答 | 无 TTL 过期应答 | 无 TTL 过期应答 |
| 2 | `192.168.229.253` | `192.168.229.253` | `192.168.229.253` |
| 3 | `49.122.23.254` | `49.122.23.254` | `49.122.23.254` |
| 4 | **`1.1.1.1`（终点）** | `10.0.2.97` | `10.0.2.97` |
| 5 | — | `10.0.4.2` | `10.0.4.2` |
| 6 | — | **`1.1.1.2`（终点）** | **`10.201.255.254`（终点）** |

到 `1.0.0.1` 的追踪也经过 `192.168.229.253 → 49.122.23.254 → 10.0.2.97 → 10.0.4.2 → 10.199.1.2 → 10.200.1.14`，但在本次 **8 跳上限内没有到达终点**。Ping 单独记录了 `1.0.0.1` 的回复。

## 12.4 目标 IP、TCP 与 DNS 样本

| IP 目标 | 一次 Ping 的 RTT | TTL | TCP 测试（约 1.1 秒超时） |
| --- | ---: | ---: | --- |
| `1.1.1.1` | 小于 1 ms | 61 | 53、443 均主动拒绝 |
| `1.1.1.2` | 小于 1 ms | 250 | 53、443 均主动拒绝 |
| `1.0.0.1` | 99 ms | 46 | 53 可连接、443 超时 |
| `1.1.1.3` | 86 ms | 46 | 未测 |
| `8.8.8.8` | 单次 Echo 超时 | — | 53 可连接 |
| `223.5.5.5` | 16 ms | 111 | 53 可连接 |

这里「主动拒绝」是 TCP 客户端收到连接失败/拒绝的报告，不代表已证明由最终目的地发回 RST。由于没有同步抓包，也不能断言一定是校园网哪个节点生成的。

使用 `nslookup`：
- 明确指定 `114.114.114.114` 查询 `example.com` 成功，返回 A 和 AAAA 记录。
- 明确指定 `10.3.0.3` 查询 `example.com`（1 秒）与 `xuhuaai.top`（2 秒）均超时。这仅是本机、当时、相关查询的结果，可能还受 DNS 服务状态、路由或访问策略影响，尚不能称为永久不可达。

## 12.5 已确认与未解决

确认：不同于前两台的第三个有线接入子网 `192.168.245.0/24`；与前期相同的 `192.168.229.253` 和 `49.122.23.254` 共同上游；`1.1.1.1`、`1.1.1.2` 仍然出现异常低 RTT、特殊跳数与 TCP 拒绝。

未解决：这些地址的真正应答端、不同校园网段是否共享一个物理 H3C 网关或网关集群、`10.3.0.3` 超时的成因、两台其他 Win7 是否处于可互访的认证/防火墙状态。

完整跨网段解释及与 [11](11-Win7第二接入点243网段观察.md) 的对照见 [13](13-跨网段公网IP异常路径对照.md)。

**后续实测（同日稍晚）**：见 [14-Win7 第三接入点 DNS 与公网出口复核](14-Win7第三接入点DNS分流与公网出口复核.md)。直接 UDP 查询使 `1.1.1.1`、`1.1.1.2` 返回 Socket ConnectionReset，而云端同样 DNS 请求成功；同时发现本轮 TCP 连接多数超时（早轮曾报告拒绝），以及自有云日志确认 `171.15.162.x` 出口。两轮结论保留其时间差异，不以新结果覆盖旧数据。仅记录已观察到的目标，不开展第三方终端发现或绕过访问控制的测试。
