# 09-邻居 192.168.236.48 的 SMB 方言与签名协商

> 观察日期：2026-11-06。目标仅为获准检查的 `192.168.236.48:445`。测试在 Win7 上通过 TCP 直连发送 SMB 协议协商报文，未发送 SESSION_SETUP、TREE_CONNECT、认证凭据或文件请求。未枚举共享和用户。

## 9.1 结论摘要

| 项目 | 实测结果 |
| --- | --- |
| TCP/445 | 可连接 |
| SMB2 多协议入口 | 成功 |
| SMB2 协商响应方言 | `0x02FF`，表示 SMB2.1 或更高版本，需后续协商 |
| 后续 SMB2 方言协商 | **`0x0210`，SMB 2.1** |
| SMB2 签名 | enabled=1，required=0 |
| SMB2 最大 Read | 1,048,576 bytes |
| SMB2 最大 Write | 1,048,576 bytes |
| SMB1 单独协商 | 成功 |
| SMB1 方言 | `NT LM 0.12` |
| SMB1 SecurityMode | `0x03` |
| SMB1 用户级安全 | 已启用 |
| SMB1 challenge-response 密码机制 | 已启用 |
| SMB1 签名位 | enabled=0，required=0 |

**关键判断：目标同时接受 SMB1 和 SMB2.1 协商。** SMB2.1 是本次客户端提供的最高方言，因此不能据此断言它不支持 SMB3；本次没有测试 SMB3 方言。

## 9.2 SMB2 多协议协商过程

### 第一次：多协议 SMB_COM_NEGOTIATE

向 TCP/445 发送标准多协议协商请求，方言列表包含：

- `NT LM 0.12`
- `SMB 2.002`
- `SMB 2.???`

服务端返回：

```text
SMB signature: FE 53 4D 42
Status:        0x00000000 (STATUS_SUCCESS)
Dialect:       0x02FF
```

`0x02FF` 是 SMB2 wildcard dialect，表示服务端实现 SMB2.1 或未来方言，客户端应继续发送 SMB2 NEGOTIATE 以选择实际方言。参考 [MS-SMB2 1.7 Versioning and Capability Negotiation](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-smb2/fac3655a-7eb5-4337-b0ab-244bbcd014e8)。

### 第二次：SMB2 NEGOTIATE

在同一 TCP 会话上继续发送 SMB2 NEGOTIATE，客户端方言列表只提供：

- `0x0202`：SMB 2.0.2
- `0x0210`：SMB 2.1

服务端响应：

```text
SMB signature: FE 53 4D 42
Status:        0x00000000
StructureSize: 65
DialectRevision: 0x0210
SecurityMode:  0x0001
MaxReadSize:   1048576
MaxWriteSize:  1048576
```

因此目标明确支持 SMB 2.1。由于请求没有提供 SMB 3.x 方言，这一结果只说明目标至少支持 SMB 2.1，**不代表 SMB 2.1 是服务端最高支持版本**。

SecurityMode `0x0001` 的解释：

- `SMB2_NEGOTIATE_SIGNING_ENABLED = 0x0001`：服务端支持 SMB 签名。
- `SMB2_NEGOTIATE_SIGNING_REQUIRED = 0x0002`：该位未设置，服务端没有在本次协商中要求客户端必须签名。

微软规范：[SMB2 NEGOTIATE Response](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-smb2/63abf97c-0d09-47e2-88d6-6bfa552949a5)。

## 9.3 SMB1 单独协商

另开 TCP 连接，单独提供 SMB1 方言 `NT LM 0.12`，不提供 SMB2 方言。服务端返回 SMB1 NEGOTIATE Response：

```text
SMB signature: FF 53 4D 42
Status:        0x00000000
WordCount:     17
DialectIndex:  0
SecurityMode:  0x03
```

DialectIndex=0 对应请求中的第一个也是唯一一个方言 `NT LM 0.12`，所以这次 SMB1 协商成功。它独立证明 SMB1 兼容协议仍然启用。

SMB1 SecurityMode 位含义：

| 位 | 掩码 | 本次 |
| --- | --- | --- |
| User-level security | `0x01` | 已设置 |
| Encrypted passwords / challenge-response | `0x02` | 已设置 |
| SMB signing enabled | `0x04` | 未设置 |
| SMB signing required | `0x08` | 未设置 |

因此 `0x03` 表示用户级安全与 challenge-response 机制已启用；本次响应没有宣告 SMB1 签名启用。微软 CIFS 规范明确规定，若响应没有设置签名 enabled 位，客户端应将服务器签名状态视为 Disabled：[MS-CIFS Receiving an SMB_COM_NEGOTIATE Response](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-cifs/8ab14111-9b41-4ede-ac94-dbea557451c6)。

## 9.4 安全含义与限制

- SMB1 仍然可协商，说明目标保留旧协议兼容面。SMB1 版本老旧，后续应优先确认设备所有者是否仍需要它。
- SMB1 响应未宣告签名能力；在 SMB1 会话中，消息签名不能从本次协商结果得到保证。
- SMB2.1 宣告支持签名但未要求签名。是否实际签名还取决于客户端是否要求签名及最终会话协商。
- SMB1 SecurityMode 的 `0x02` 表示 challenge-response 机制，不等于密码明文传输，也不代表认证已发生。
- 本次没有发送 SESSION_SETUP，因此没有尝试认证，也没有判断账号、密码、Guest 或匿名访问策略。
- 本次没有发送 TREE_CONNECT，因此没有列举共享名称、权限或文件。
- SMB2.1 是客户端所提供方言集合中的最高项，目标可能还支持 SMB3.x；需要另行设计含正确能力与协商上下文的 SMB3 探测，不能从当前结果推断 SMB3 不存在。
- 目标设备型号、操作系统、实际 SMB 服务实现仍未确认。SMB 2.1 和 SMB1 共存可以出现在旧 Windows、Samba 或嵌入式 NAS/打印设备等多种实现中。

## 9.5 对校园网研究的意义

结合此前对 `192.168.236.48` 的观察：

- 同一 /24 内 ICMP 可达，TTL=64。
- ARP OUI 为 `44:37:E6`，注册组织为鸿海；完整 MAC 不公开。
- TCP/445 可连接，且已证实提供 SMB1 与 SMB2.1 协议协商。
- 反向 DNS 超时，NetBIOS 名称表查询没有返回结果；`ping -a` 曾解析为本机名 `a307`，该名称异常仍未解释。

这台邻居很可能是提供 SMB 文件共享能力的终端或嵌入式设备，但仅凭 SMB 方言和 OUI 无法识别具体设备类型。若要继续识别，应先由所有者确认设备用途；本研究暂时停留在未认证的协议协商阶段。

## 9.6 下一步

1. 询问设备所有者是否预期启用 SMB 文件共享，以及是否需要 SMB1 兼容性。
2. 如有授权，使用方言列表包含 SMB 2.0.2、2.1、3.0、3.0.2、3.1.1 的规范协商请求，正确提供 SMB 3.1.1 的 pre-authentication integrity context，确认服务端最高支持方言。
3. 若目标所有者明确授权，再决定是否进行只读的 SMB 会话设置与共享清单检查；不得尝试猜测凭据或读取文件内容。

本次没有修改目标设备配置。
