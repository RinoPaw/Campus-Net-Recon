# 10-校园网跨区域公网出口与有线接入路径实测

> 2026-11-06，研究重点回到校园网本身。本篇只使用已授权接入的 Win7 教室有线终端、自有宿舍 OpenWrt，以及自有腾讯云 HTTPS/Nginx 服务。**核心发现：Win7 和宿舍 OpenWrt 对同一公网服务器使用不同的公网源地址，且逐跳路径不同。** 本文区分已验证的事实、可疑路径与待测试假设，不涉及对其他终端的服务枚举。

## 10.1 为什么进行这轮实验

先前的 [05](05-Win7有线接入网关与跨域回程观察.md)、[06](06-东区西区15分区假设与Win7教室接入定位.md) 已确认：
- Win7 静态 IPv4：`192.168.236.49/24`；默认网关：`192.168.236.254`；
- Win7 上游路径可观察到 `192.168.229.253`、`49.122.23.254`、`10.0.2.97`、`10.0.4.2`；
- 宿舍 OpenWrt 上联为 `10.202.255.254/13`，默认网关为 `10.203.255.254`；
- Win7 对 `10.202.255.254` 的 ICMP Echo 可得到回复，而 OpenWrt 对 Win7 的 `192.168.236.49` 没有取得回复；**Win7 Echo 的应答端身份仍需验证**；
- 东区 `10.200.0.0/15`、西区 `10.202.0.0/15` 是尚未获得校园网官方资料确认的区域地址分配假设。

这轮研究回答的问题：**Win7 和宿舍 OpenWrt 是不是经过同一公网出口？流量在什么位置开始分叉？**

## 10.2 通过自有云服务器观测真实公网源地址

步骤：

1. Win7 在 PowerShell 2.0 中以 `.NET HttpWebRequest` 直接访问自有站点 `http://xuhuaai.top/route-probe/win7-a307-20261106-1651`，设置 `AllowAutoRedirect = false`；收到 HTTP 301。
2. 宿舍 OpenWrt 通过 `wget` 访问同域名不同的唯一标记路径 `/route-probe/openwrt-20261106-1652`；收到 HTTP 301，后续自动跟随到 HTTPS。
3. 在自有腾讯云 Nginx 访问日志中按照两条唯一标记核对客户端源 IP、时间、HTTP 状态码。请求无账号、Cookie 或其他个人内容；没有测试第三方服务。

| 测试源 | 本机接口 IPv4 | Nginx 所见公网源 IP | 状态 |
| --- | --- | --- | --- |
| Win7 教室有线 | `192.168.236.49/24` | `171.15.162.x`（完整地址保留于自有服务器原始访问日志） | HTTP 301 |
| 宿舍 OpenWrt 校园 Wi-Fi | `10.202.255.254/13` | `39.162.143.x`（完整地址保留于自有服务器原始访问日志） | HTTP 301，随后 HTTPS |
 
**可证实：** 同一时刻两条公网 HTTP 连接的外部可见源地址不同，且与各自的私网源地址不同。两端经过了不同的地址转换/出口路径（这里的“源地址转换”也可能发生在中间级设备，而不一定在本机默认网关上）。

**不能据此证实：** NAT 的具体设备、次数、转换规则、是否有多个出口负载均衡，以及校内互访流量是否走相同 NAT 规则。公网源 IP 属于动态观察值，之后可能变化。
### 排除 Win7 系统代理：原始 TCP 直连复测

之前的 `.NET HttpWebRequest` 可能使用系统代理，因此重新核对代理配置，并绕过 HTTP API 直接建立 TCP 连接：

- `netsh winhttp show proxy`：直接访问（无代理服务器）。
- 当前用户 Internet Settings：`ProxyEnable=0`；没有配置 `ProxyServer` 或 `AutoConfigURL`。
- `.NET DefaultWebProxy.GetProxy(http://xuhuaai.top/)` 返回原始目标 URL，没有改写到代理地址。
- 使用 `System.Net.Sockets.TcpClient` 直接连接 `xuhuaai.top:80`，DNS 解析为 `62.234.68.123`；手工发送 HTTP 请求，收到 `301`。
- Nginx 记录唯一标记 `win7-direct-20261106-1720`，来源仍为 `171.15.162.4`（公开文档脱敏为 `171.15.162.x`）。

宿舍 OpenWrt 也复测了直连：

- `env | grep -i proxy` 没有代理环境变量。
- `ip route get 62.234.68.123` 返回 `via 10.203.255.254 dev phy-sta1 src 10.202.255.254`。
- BusyBox `wget` 直接解析并连接 `62.234.68.123:80`；Nginx 对唯一标记 `openwrt-direct-20261106-1732` 记录的来源仍为 `39.162.143.1`（公开文档脱敏为 `39.162.143.x`）。

**修正结论：** 两个公网源地址差异不是由 Win7 系统 HTTP 代理造成的。Win7 原始 TCP 和 OpenWrt 无代理 HTTP 请求分别从不同公网源地址到达自有服务器，足以确认两种接入路径存在不同的公网出口/NAT 映射。


### 公网出口的 ASN / 运营商归属

对 Nginx 观察到的公网出口地址段做独立的 BGP/WHOIS 检索：

| 来源 | 地址段（脱敏） | 公网路由 ASN | 注册运营商 |
| --- | --- | --- | --- |
| Win7 有线 | `171.15.162.x` | **AS4134** | 河南电信 / CHINANET-HA |
| 宿舍 OpenWrt | `39.162.143.x` | **AS24445** | 河南移动 / CMNET-V4HENAN |

参考公开登记：[171.15.0.0/16 — AS4134 / CHINANET-HA](https://ipregistry.co/AS4134/171.15.0.0/16)，[39.162.143.0/24 — AS24445 / 河南移动](https://ipinfo.io/ips/39.162.143.0/24)，[AS24445 路由前缀](https://bgp.he.net/AS24445)。

**结论强化：** 这两种接入方式经不同运营商出口。它可能受接入位置、网络类型、有线/Wi-Fi、套餐或路由策略影响；单凭两台设备的结果尚不能建立“东区必走电信、西区必走移动”的一般规则。IP 运营商登记也不能直接说明接入到运营商的实际物理互联点位置。

## 10.3 到同一个腾讯云目标的逐跳路径

从 Win7 执行 `tracert -d -h 10 -w 130 62.234.68.123`：

```text
hop 1: * * *                 [本机默认网关为 192.168.236.254；不回应 TTL=1 探测]
hop 2: 192.168.229.253
hop 3: 49.122.23.254
hop 4: 10.0.2.97
hop 5: 10.0.4.2
hop 6: * * *
hop 7: 10.200.1.14
hop 8: 171.15.162.1
hop 9: 222.85.12.29 (部分探测有回应)
hop 10: * * *
```


补充一轮 Win7 当前路径（`tracert -d -h 10 -w 250 62.234.68.123`）：

```text
1  * * *
2  192.168.229.253
3  49.122.23.254
4  10.0.2.97
5  10.0.4.2
6  10.199.1.2
7  10.200.1.14
8  171.15.162.1
9  222.85.12.29 (部分探测有回应)
```

同时，Win7 `route print -4` 的活动路由仅包含本地 `192.168.236.0/24`、回环/组播路由及默认路由 `0.0.0.0/0 via 192.168.236.254`；没有针对 `10.0.0.0/8` 或 `10.200.0.0/13` 的专用路由。因此 Win7 发往校园 `10.x.x.x` 的目标均交给本地网关 `192.168.236.254`，再由上游决定路径。

从宿舍 OpenWrt 执行 `traceroute -n -m 10 -w 1 -q 1 62.234.68.123`：

```text
hop 1: *
hop 2: 10.200.1.5
hop 3: *
hop 4: 111.5.141.49
hop 5–10: *
```

这两次分别使用 Windows ICMP 与 OpenWrt 默认 traceroute（通常采用 UDP 探测），因此不能把跳数或未响应节点直接作严格的一一比较。但从已响应的节点看，Win7 方向出现 `10.200.1.14` 和 `171.15.162.1`，宿舍方向出现 `10.200.1.5`、`111.5.141.49`，显示出不同的可观测路径。

## 10.4 到自有宿舍 OpenWrt 的访问行为

- Win7 `ping -n 4 10.202.255.254`：4/4 收到 Echo Reply，约 1–2 ms；历史测试中多次成功，回复 TTL 为 58。
- Win7 发起到 `10.202.255.254:80` 的 TCP 连接：连接被拒绝。这只说明此路径下 TCP/80 没有完成握手，**不能排除防火墙拒绝或路由转发策略**。
- 在 OpenWrt 安装 `tcpdump-mini` 和 `libpcap1` 以进行短时、定向抓包；未修改路由、NAT、认证或防火墙规则。
- 首次使用仅限定 `icmp and dst host 10.202.255.254` 的过滤器，捕获到其他 ICMP 响应报文，无法归属 Win7；该次结果**不算 Win7 的源 IP 证据**。
- 随后改用仅限 ICMP Echo Request (`icmp[0] = 8`) 的过滤器，在同步 Ping 时没有捕获到对应请求，最终超时。再次使用 `phy-sta1` 上的宽松定向过滤器（`icmp and dst host 10.202.255.254`）持续抓取 12 秒；Win7 同期发送 **5 个 500 字节 Echo Request** 且收到 5 个回复，OpenWrt 只看到两个无关的 64 字节 ICMP Echo Reply，**未看到与 Win7 500 字节请求相符的报文**。另外，以 OpenWrt 自己向 `10.203.255.254` 发起的 ICMP Echo 验证过 `tcpdump` 可以正常捕获自有接口的数据包（计数无丢包）。这一异常需要优先核实：`10.202.255.254` 的实际应答者是否就是这台 OpenWrt，抑或存在其他网络设备响应相同目的地址；以及上游是否改写了目的地址或使用非预期转发路径。**目前不能根据空抓包单独证明 NAT、IP 冲突、代理应答或欺骗。**


补充的 Win7 同一时段路由追踪：

| 目标 | 共同路径 | 终点 |
| --- | --- | --- |
| `10.201.255.254` | `192.168.229.253 → 49.122.23.254 → 10.0.2.97 → 10.0.4.2` | 第 6 跳 `10.201.255.254` |
| `10.203.255.254` | 同上 | 第 6 跳 `10.203.255.254` |
| `10.202.255.254` | `192.168.229.253 → 49.122.23.254 → 10.0.2.97 → 10.0.4.2 → 10.199.1.2` | 第 7 跳 `10.202.255.254` |

这再次显示 `10.201.255.254` 与 `10.203.255.254` 是两个共享上游路径的候选区域网关；`10.202.255.254` 是另一个多一跳的目标地址。OpenWrt 本机 `ip route get 10.202.255.254` 返回 `local 10.202.255.254 dev lo table local`，证明本机内核确实把该地址视为自身地址；但 Win7 的应答是否来自本机仍未得到抓包支持。

因此，Win7 到 `10.202.255.254` 的实际应答设备身份和内部转发策略都仍是未解问题。抓包完成后已经卸载临时安装的 `tcpdump-mini` 与 `libpcap1`，路由器的软件包清单恢复到测试前的 194 包规模。

## 10.5 当前可以推出的最小网络模型

```text
Win7 教室有线
  192.168.236.49/24
  -> 本地网关 192.168.236.254
  -> 192.168.229.253
  -> 49.122.23.254
  -> 10.0.2.97 / 10.0.4.2
  -> [校内路由/公网出口，设备与 NAT 位置待证实]
  -> 公网观测源 171.15.162.x

宿舍 OpenWrt 校园 Wi-Fi
  10.202.255.254/13
  -> 网关 10.203.255.254
  -> 10.200.1.5（traceroute 可见）
  -> [校内路由/公网出口，设备与 NAT 位置待证实]
  -> 公网观测源 39.162.143.x
```

此前提出的“东区为 `10.200.0.0/15`、西区为 `10.202.0.0/15`”仍可作为待检验的地理地址规划假设。Win7 当前处于 `192.168.236.0/24` 的私有有线子网，尚无证据证实这一私网具体属于东区的哪台汇聚设备或 VLAN。

## 10.6 下一步优先级

1. **先确认 IP 应答者身份**：当前 Win7 对 `10.202.255.254` 的 Ping 成功，但 OpenWrt 未观察到相应请求。若要进一步验证，应在不改变现网路由的前提下，通过自有设备进行可识别的端到端探测，或检查有授权的校园网接入设备日志。目标是确定该地址是否存在冲突、代理响应或路径转换，再讨论 NAT 源地址。
2. 仅在两个自有端点间复测不同协议（ICMP 和 TCP）的连通性，区分策略阻断和 NAT 回程问题。
3. 使用同一探测协议和时间窗口，对比 Win7 与 OpenWrt 到同一自有云服务器的路径，减少 Windows tracert 与 OpenWrt traceroute 方法不同造成的偏差。
4. 如能取得正规校园网文档或自有接入路由器/交换机的管理资料，核对有线 `192.168.236.0/24` 的归属与 `10.201.255.254` 的网关分组关系。

**研究边界：** 只使用本人设备与获准测试的网络范围，不访问其他终端、认证系统或网关管理入口，不修改校园网配置。对公网出口 IP 进行脱敏后再公开。
