# 15-Win7 原生 ICMP 抓包：从 UDP/53 错误追踪到 `10.0.2.10`

> **实验日期：2026-11-13（UTC+08:00）**，在自有/获授权的 Win7 SP1 32 位有线设备 `win7-3` 上完成。研究基于 [12](12-Win7第三接入点245网段观察.md)、[13](13-跨网段公网IP异常路径对照.md)、[14](14-Win7第三接入点DNS分流与公网出口复核.md)；本篇包含新取得的实际 IPv4/ICMP 报文头证据。没有修改校园网任何设置，没有安装 WinPcap/Npcap/Wireshark，也没有采集、保存无关终端流量。

## 15.1 核心发现

**针对 `1.1.1.2:53` 发起的 UDP DNS 请求，在本机实际收到源地址为 `10.0.2.10` 的 ICMP Type 3 / Code 3（Destination Unreachable / Port Unreachable）错误。**

这个错误报文包含引用的原始 UDP 数据包头：源 `192.168.245.38`，目的 `1.1.1.2`，协议 UDP，目的端口 53。由此可以确认它是与本次目标 DNS 请求匹配的错误，而不是仅凭 DNS 客户端呈现的 `ConnectionReset` 猜测。

对 `1.1.1.1:53` 的请求则收到**源地址标记为 `1.1.1.1`**、同为 Type 3 / Code 3 的 ICMP 错误；该源 IP 可能由上游策略设备作为错误应答源地址使用，尚不能直接确认是真实公网服务器发来的。

## 15.2 实验条件与方法

- 测试终端：`win7-3`，Windows 7 SP1 **32 位**，PowerShell 2.0，`192.168.245.38/24`，默认网关 `192.168.245.254`。
- 首先检查本机权限及现有工具：当前 PowerShell 具有高完整性管理员权限；没有发现 Wireshark、Npcap/WinPcap 驱动/服务。
- 利用 Windows 内置 `System.Net.Sockets.Socket` 的 IPv4 Raw Socket + `IOControlCode.ReceiveAll` 在当前本机接口开启**短时内存抓包**。接收层会看到该接口的报文，但脚本只解析与三个指定公网 DNS 目标有关的 ICMP 误差报文，**其余流量立即丢弃，不落盘，也不输出**。
- 同时发送极少量标准 DNS `example.com A` 请求到 `1.1.1.1`、`1.1.1.2`、`1.0.0.1` 的 UDP/53，读取抓到的外层 IPv4 源 IP、TTL、ICMP 类型/代码和 ICMP 引用中的原始 IP/UDP 目的地址和端口。
- 每轮捕获约 6–8 秒，全部只读、定向，没有改变路由、防火墙、网关或网络认证状态。原始报文仅在内存中短时解码。

可复现脚本：[scripts/observe-icmp-dns-win7.ps1](../scripts/observe-icmp-dns-win7.ps1)。该文件已在**实际 win7-3 的 PowerShell 2.0 环境**中通过解析检查，并以脚本块在内存中执行，复现了两条 ICMP 错误；临时测试文件已删除。该主机的常规脚本文件执行策略为 Restricted，如果直接以 `.ps1` 文件运行会被拦截；需要在受控会话中按本机策略使用进程范围的执行参数，不建议永久改变全局执行策略。

## 15.3 实际原始报文摘要

第一次原始抓包（按报文头和内层引用字段整理）：

| 原始 UDP 请求目的地 | ICMP 外层源 IP | 外层 TTL | ICMP Type/Code | 收到的 IP 包字节数 | 被引用的 UDP 原始目的地 |
| --- | --- | ---: | --- | ---: | --- |
| `1.1.1.1:53` | **`1.1.1.1`** | 61 | **3/3** | 85 | `192.168.245.38 → 1.1.1.1:53` |
| `1.1.1.2:53` | **`10.0.2.10`** | 250 | **3/3** | 56 | `192.168.245.38 → 1.1.1.2:53` |
| `1.0.0.1:53` | 无相关错误，DNS 响应成功 | — | — | — | 正常返回 DNS 数据 |

两种错误报文长度不同（85 vs 56 字节），来源 IP 和 TTL 也不同，这与**不同 ICMP 错误生成机制或实现**相容，但包长度不同本身不能用来确定操作系统、品牌或物理设备身份。

第二轮对前两个 DNS IP 各发送两次请求：观察到 `1.1.1.1` 对应的两条 Type 3/Code 3、`1.1.1.2` 对应的一条 Type 3/Code 3。由于短时抓取没有收到第二条 `1.1.1.2` 错误，不应称其每次请求都会收到相同错误，可能存在丢包、限速或其他差异。

随后对仓库里的独立复现脚本进行**现场运行**：再次捕获 `src=1.1.1.1, quoted_dst=1.1.1.1:53, ttl=61` 和 `src=10.0.2.10, quoted_dst=1.1.1.2:53, ttl=250`，并确认 `1.0.0.1` 得到 DNS 成功响应。因此这两种 ICMP 来源已经在多个短时轮次复现。

## 15.4 内部节点 `10.0.2.10` 的路径复核

在确认 ICMP 报文源地址后，对该**已观察到的网络节点**做两次 Ping 和一次 7 跳上限 traceroute：

- `ping 10.0.2.10`：2/2 收到回复，RTT 小于 1 ms，TTL **250**；
- `tracert -d -h 7 -w 150 10.0.2.10`：目标在第 **6** 跳回应。

对照相同 Win7 到 `1.1.1.2` 的路由追踪：

| TTL / 跳数 | `1.1.1.1` | `1.1.1.2` | `10.0.2.10` |
| ---: | --- | --- | --- |
| 1 | 网关不回应 TTL 过期 | 网关不回应 | 网关不回应 |
| 2 | `192.168.229.253` | `192.168.229.253` | `192.168.229.253` |
| 3 | `49.122.23.254` | `49.122.23.254` | `49.122.23.254` |
| 4 | **`1.1.1.1` 应答** | `10.0.2.97` | `10.0.2.97` |
| 5 | — | `10.0.4.2` | `10.0.4.2` |
| 6 | — | **`1.1.1.2` 应答** | **`10.0.2.10` 应答** |

额外对 `1.1.1.1`、`1.1.1.2` 发送**少量不同出站 TTL 的 Ping**也重现：TTL 2、3 时分别收到 `192.168.229.253`、`49.122.23.254` 的超时信息；`1.1.1.1` 到 TTL 4 开始回应；`1.1.1.2` 则依次通过 `10.0.2.97`、`10.0.4.2` 后在 TTL 6 开始回应。这个结果与 traceroute 的跳数一致。

两者都在第六跳、RTT 小于 1 ms、回复 TTL 250，同时 `10.0.2.10` 生成了指向 `1.1.1.2` DNS 查询的 ICMP 错误，**强烈支持 `1.1.1.2` 在这条访问路径上与 `10.0.2.10` 附近的同一策略设备或网络设备组有关**。还不能认定两个 IP 实际绑定同一物理接口、同一台硬件，或定性为特定安全设备类型。设备可以用多个 IP 回应，也可能通过路由、NAT、ACL 或代理应答实现类似现象。

## 15.5 证据结论和下一步

**直接证实：** Win7 收到符合此次 DNS 请求的 ICMP Port Unreachable；`1.1.1.2` 对应错误的外层 IP 源为 `10.0.2.10`（不只是普通 DNS 超时）；`1.1.1.1` 对应错误的外层源为 `1.1.1.1`；两个目标的可见跳数不同，`10.0.2.10` 和 `1.1.1.2` 在此接入网里具有一致的第六跳与 TTL 特征。

**尚待证实：** 谁实际生成了 `1.1.1.1` 的源地址标记；`10.0.2.10` 的具体物理设备或虚拟接口归属；针对两个 IP 的特殊处理是否由同一项网关/策略路由/安全控制配置实现；新旧 Win7 在其他接入区域是否共用相同规则。

下一步要取得新的机制结论，优先核对经授权的网管/路由配置，或在其他本人可控网络点同协议地复测；不要使用推测替代缺失的设备日志。对用户不管理的网络设备不进行口令尝试、漏洞测试、全网扫描或配置修改。
