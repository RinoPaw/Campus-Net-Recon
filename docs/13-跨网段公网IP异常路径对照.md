# 13-跨接入网段对照：1.1.1.1 / 1.1.1.2 特殊路径

> 汇总日期：**2026-11-13**。资料来源：[05](05-Win7有线接入网关与跨域回程观察.md)（2026-11-06）、[11](11-Win7第二接入点243网段观察.md)（2026-11-10 历史观测）、[12](12-Win7第三接入点245网段观察.md)（2026-11-13 当日实测）。本文是多接入点证据汇总，**不代表三个设备在同一时刻运行过完全相同的实验**。

## 13.1 研究问题

多个独立的 Windows 7 有线接入子网都见到 `1.1.1.1` 的异常低延迟，且不同 IP 的端口行为分化。现在需要区分：

1. 现象是单一电脑/本机 DNS/本机代理造成，还是多个网段可重复观测的上游行为？
2. 本地网关是否共享同一个校内转发核心？
3. 特殊 IP 的应答方究竟是谁？**目前未证实**，不能将「4 跳到达 1.1.1.1」直接当作抵达真实互联网服务。

## 13.2 三台 Win7 的接入环境

| 观察来源 | 本地 IPv4 | 默认下一跳 | 网关 MAC OUI | 备注 |
| --- | --- | --- | --- | --- |
| [05] 首台 Win7 | `192.168.236.49/24` | `192.168.236.254` | `60:0B:03` | 2026-11-06 有线采样 |
| [11] `win7-2` | `192.168.243.77/24` | `192.168.243.254` | `60:0B:03` | 2026-11-10 有线采样摘要 |
| [12] `win7-3` | `192.168.245.38/24` | `192.168.245.254` | `60:0B:03` | 2026-11-13 有线采样 |

三台均通过本地私有 `192.168.x.254` 网关进入校园网络。MAC 前缀注册组织是 H3C，但**相同 OUI ≠ 相同物理交换机或同一虚拟网关**。不同主机的认证状态和具体房间位置没有完整的同期记录。

## 13.3 共享上游与不同目标路径

三台均观察到以下代表性中间节点：

```text
各自的 192.168.{236,243,245}.254
    ↓（在 traceroute 中可能不回应 TTL 过期）
192.168.229.253
    ↓
49.122.23.254         (CERNET 登记地址空间)
    ├─→ 1.1.1.1        (两台新 Win7：第 4 跳得到终点回应)
    └─→ 10.0.2.97
             ↓
         10.0.4.2
             ├─→ 1.1.1.2       (win7-3 第 6 跳得到终点回应)
             ├─→ 10.201.255.254 / 10.203.255.254
             └─→ 后续其他内部或公网路径
```

此图仅代表多次 **tracert 的逻辑路径**，分支不代表已确认的物理接口连接。第 4 跳出现公网目标地址可能意味着本地应答、特殊路由或中间设备相关机制；需要同步抓包、其他独立网络出口测量或授权设备日志才能识别。

Win7 对 `10.201.255.254`、`10.203.255.254` 的追踪也呈现 `192.168.229.253 → 49.122.23.254 → 10.0.2.97 → 10.0.4.2` 的相同前缀。这加强了**不同有线接入子网共用一段上游路径**的判断，但不能确定对应 VLAN 或 SNAT 实施位置。

## 13.4 两个不同网段对相同公网地址的复现

| 目标 | `win7-2` 2026-11-10 | `win7-3` 2026-11-13 | 判读 |
| --- | --- | --- | --- |
| `1.1.1.1` | 约 0–4 ms，TTL 61；约第 4 跳 | 小于 1 ms，TTL 61；第 4 跳 | 强一致，异常低时延 |
| `1.1.1.2` | 小于 1 ms，TTL 250 | 小于 1 ms，TTL 250；第 6 跳 | TTL/时延复现 |
| `1.0.0.1` | 约 83 ms，TTL 46 | 99 ms，TTL 46 | 与前两地址明显不同 |
| `1.1.1.3` | 约 85–86 ms，TTL 46 | 86 ms，TTL 46 | 较长外部路径特征 |
| `223.5.5.5` | 约 16 ms | 16 ms | 对照目标 |
| `8.8.8.8` | 曾约 183 ms | 单次 Ping 超时 | 不同时间、样本太少，不推断稳定变化 |

两台新 Win7 上，`1.1.1.1` 和 `1.1.1.2` 的 TCP 53 / 443 连接均报告「拒绝」，而 `1.0.0.1:53` 均可连接。单次拒绝不一定由实际目的 IP 发回，不应据此将 ICMP 应答者、TCP 拒绝者和最终目标服务混同。

`win7-3` 的 `10.3.0.3` DNS 在两轮短查询中超时，而 `114.114.114.114` 查询成功。这是另外一条 **DNS 服务可用性差异**，并不能直接解释上述以裸 IP 发起的 ICMP/TCP 测试。

**2026-11-13 同日补充对照：** 新实验用相同的原始 UDP DNS 查询分别从 `win7-3` 和自有腾讯云访问 `1.1.1.1`、`1.1.1.2`：Win7 均收到 Socket `ConnectionReset`，而云端均得到有效 DNS 响应；对照 `1.0.0.1` 在两端均成功。自有 Nginx 访问日志又确认 `win7-3` 实际公网出口与第一台 Win7 使用相同 `171.15.162.x` 电信地址范围，且到云服务器的前九跳观测一致。另一次 TCP 测试则表现为超时，和早轮的「拒绝」不同；未判明是否为动态策略。详细命令、样本和证据边界见 [14](14-Win7第三接入点DNS分流与公网出口复核.md)。

**同日抓包补充：** [15-Win7 原生 ICMP 抓包](15-Win7原生ICMP抓包定位DNS拒绝应答者.md) 在 `win7-3` 上找到针对 `1.1.1.2:53` 的 ICMP 端口不可达，其报文源地址为 `10.0.2.10`；该地址与 `1.1.1.2` 都在第 6 跳回应，TTL 为 250。这加强了上游特定处理的证据，但仍未识别实际物理设备及配置。以下对「应答者未知」的表述以这一补证为准。

## 13.5 当前结论与证据等级

**强证据：**
- `192.168.243.0/24` 和 `192.168.245.0/24` 两个独立有线接入网段出现同一组异常目标 IP 时延、TTL 和 TCP 连接特征。
- 这两台 Win7 使用不同的 DNS 设置，故「某台 Windows 的 DNS 设置」不能单独解释对裸 IP 的测试结果。
- 各有线网段通过 `192.168.229.253` 和 `49.122.23.254` 等共享的可见上游节点。

**有限旁证：**
- 三个有线网关的相同 H3C OUI，以及 `win7-3` 到多个其他 `.254` 网关的低延迟与 TTL 255，支持集中/共同的网关系统模型，但不足以判断物理拓扑。

**仍属假设：**
- 是否有特定路由、PBR、地址映射、防火墙主动拒绝或代理回应针对 `1.1.1.1/1.1.1.2` 生效。
- 策略实施点是否恰在 `49.122.23.254`、它前面或后面。
- 这些观察是否和认证状态、校区位置、时间段相关。
- `192.168.236.49` 与新两台 Win7 是否可以互相直接通信。新的单次 Ping 超时不足以证明隔离。

## 13.6 下一次记录应补充什么

- 同一时间窗口、相同命令及相同目标，从已获授权的至少两个接入点测量；记录完整日期、IPv4/网关、代理、DNS、TTL、延时样本数及失败类型。
- 对可管理的自有腾讯云端点做请求日志比对，明确网络路径和实际收到的源地址；不能用公网服务的 Ping RTT 代替到达证明。
- 如获得校园网运维人员提供的路由/ACL/VRF/PBR 资料，再验证哪一设备生成应答或拒绝。
- 区分实验中的「收到响应」「终点服务真实可用」「报文实际经过某一物理设备」三个层级，不把一种证据当成全部结论。

研究遵循 [00 记录规范](00-记录规范与术语.md)：不大规模扫描、不探测无关第三方终端、不修改校园认证、计费、路由或防火墙。公开记录不包含完整设备 MAC、登录标识和个人信息。
