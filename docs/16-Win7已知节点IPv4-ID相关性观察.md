# 16-Win7 已知节点 ICMP Echo IPv4 ID 相关性观察

> **本篇结论：** 2026-11-13 在第三台已获授权的 Windows 7 终端 `win7-3` 上，交替向此前已发现的 `1.1.1.2` 与 `10.0.2.10` 发送少量 ICMP Echo Request，接收的 Echo Reply IPv4 Identification（IP ID）在两轮成功抓取中呈现跨源地址的连续/近连续递增。这明显加强了“共享 IP ID 分配状态或由共同上游设备处理”这一判断，但**不能据此识别具体物理设备**。

## 背景与环境

先前的 [15-原生 ICMP 抓包](15-Win7原生ICMP抓包定位DNS拒绝应答者.md) 已确认：当终端对 `1.1.1.2:53` 发起 UDP DNS 查询时，收到外层源地址为 `10.0.2.10` 的 ICMP Type 3 / Code 3；两个地址的 ICMP Echo Reply 均呈 `TTL=250`、小于 1 ms，traceroute 均在第六跳结束。此前尚未比较来自这两个源地址的 **IPv4 Identification**。

本次已知设备条件与同日 [12](12-Win7第三接入点245网段观察.md) 一致：

- 终端：`win7-3`，Windows 7 SP1，32 位，PowerShell 2.0；本地 IPv4 `192.168.245.38/24`，网关 `192.168.245.254`。
- **日期**：2026-11-13；成功命令未单独落盘精确开始时刻，不伪造秒级采样时间。
- 当前 IP 已在本轮通过 Win32_NetworkAdapterConfiguration 再次读取确认。
- 仅观察已知的 `1.1.1.2`、`10.0.2.10`，并以 `1.1.1.1` 作对照；没有对未知主机扫描。
- 不修改主机 DNS、路由、防火墙、认证或校园网设备配置。

## 操作

通过具管理员权限的 PowerShell 2.0，使用原生 .NET Raw IPv4 Socket，绑定本人设备接口并启用 `IOControlCode.ReceiveAll`，短时接收 IPv4 报文。在另一后台 PowerShell Job 里向指定目标依次发送**单个** ICMP Echo Request。

只输出以下条件满足的包：

1. IPv4 Protocol 为 ICMP（1），ICMP Type 为 Echo Reply（0）；
2. 外层 IPv4 源地址属于此次指定的三个目标之一；
3. 从外层 IPv4 首部读取 TTL、Identification、Flags/Fragment Offset、总长度。

未匹配的网络报文不输出、不保存。抓取仅在内存短时进行，无 `pcap` 文件。首次两次成功抓取均使用临时内联 PowerShell 脚本块，复现脚本已整理为 [observe-echo-ipid-win7.ps1](../scripts/observe-echo-ipid-win7.ps1)。**仓库脚本为上述已运行方法的整理版；截至 2026-11-13 初稿时尚未作为独立文件现场执行验证，2026-11-17 已完成实机验证，见文末复核。**

## 第一轮成功抓取

在同一连续捕获窗口下，向 `1.1.1.2`、`10.0.2.10` 交替发送请求，最后向 `1.1.1.1` 发出两个对照请求。终端返回：

| 捕获顺序 | Echo Reply 源地址 | TTL | IP ID | IPv4 flags/frag | IPv4 总长度 |
| ---: | --- | ---: | ---: | ---: | ---: |
| 1 | `1.1.1.2` | 250 | 21696 | 0 | 60 |
| 2 | `10.0.2.10` | 250 | 21698 | 0 | 60 |
| 3 | `1.1.1.2` | 250 | 21700 | 0 | 60 |
| 4 | `10.0.2.10` | 250 | 21701 | 0 | 60 |
| 5 | `1.1.1.1` | 61 | 30852 | 0 | 60 |
| 6 | `1.1.1.1` | 61 | 30853 | 0 | 60 |

前四条 ID 在请求交替的过程中持续上升，允许期间其他网络流量占用计数值。对照地址 `1.1.1.1` 具有不同的 TTL 和 IP ID 序列。

## 第二轮独立成功抓取

调整发送顺序为 `10.0.2.10 → 1.1.1.2 → 1.1.1.2 → 10.0.2.10`，再次在短时内存抓取中观察到：

| 捕获顺序 | Echo Reply 源地址 | TTL | IP ID |
| ---: | --- | ---: | ---: |
| 1 | `10.0.2.10` | 250 | 21797 |
| 2 | `1.1.1.2` | 250 | 21798 |
| 3 | `1.1.1.2` | 250 | 21799 |
| 4 | `10.0.2.10` | 250 | 21800 |

**本轮四个 ID 连续递增、无跳号，并且跨两个不同源地址。** 这与“单一递增 IPv4 ID 计数器被两个应答身份共享”高度一致。第二轮距离第一轮经过了一段时间，因此两轮的起始 ID 不应直接当作准确的背景流量计数或时间尺度。

另外一条较长（8 秒）的尝试出现 Reinor 远程执行超时，**没有获得可用输出**；本文未把它计为成功样本，也不声称该次收发结果。

## 解释与证据边界

- **直接观测**：两个不同源 IP 的 Echo Reply 拥有同一 TTL=250、同一长度和 flags/frag；且它们的 IPv4 ID 在两轮少量样本中跨源地址连续/近连续递增。
- **得到增强的解释**：`10.0.2.10` 与 `1.1.1.2` 的应答可能由同一个 IPv4 协议栈、同一台设备的多个地址、或共享 IP ID 生成/改写状态的中间设备系统产生。这与先前 DNS ICMP Port Unreachable 的外层源地址、以及二者同为第六跳的现象相互印证。
- **不能推出**：两个地址一定绑定同一网卡、同一物理设备，或者一定是某个特定品牌/型号的网关。IPv4 ID 可以被转发设备统一重写，多个设备也可能共享生成状态；不同栈的实现还可能有相似计数策略。
- **样本限制**：仅两轮短时成功样本，且抓包脚本只保留匹配的 ICMP Echo Reply；没有任何上游设备的原始配置、日志或者双侧同步报文证据。

## 后续方向

下一阶段应优先在**本人控制的链路和节点**上验证是否可能由转发设备统一重写 IPv4 ID，或征得校园网络运维授权核对策略设备配置。若其他受控 Win7 接入点再次在线，可在相同时间窗口进行相同小样本对照。再增加大量 Ping 不能替代设备归属证据。

沿用 [00-记录规范](00-记录规范与术语.md)：不探测无关终端，不公开个人标识，不尝试绕过认证/计费/访问控制。

## 2026-11-19：跨 ICMP 报文类型的 IP ID 计数域关联

> 本节进一步检验：同样报成 `10.0.2.10` 的 **Echo Reply** 和 **DNS Port Unreachable**，是否和 `1.1.1.2` Echo Reply 属于同一 IPv4 ID 分配状态？以及 `1.1.1.1` 的 Echo Reply、DNS 错误是否与路由节点 `10.0.2.97` 的应答相关？

所有采样均来自同一台获授权的 `win7-5`（`192.168.23.66/24`，Windows 7 SP1 64 位、PowerShell 2.0 管理员），仅针对仓库已有的 `1.1.1.1`、`1.1.1.2`、`10.0.2.10`、`10.0.2.97`。使用短时 `Raw Socket + ReceiveAll` 内存捕获，只输出符合固定 Echo 回复源或匹配指定 UDP 请求源端口的 ICMP，未保存无关流量或 PCAP。

### A. 1.1.1.2 / 10.0.2.10：Echo 共计数，但 Port Unreachable 使用不同序列

`UTC=2026-11-19T09:03:54.7137253Z`，在同一个 8 秒捕获窗口内交替 Ping `1.1.1.2`、`10.0.2.10`，并向 `1.1.1.2:53` 发送三次固定 DNS UDP 请求。观察到下列 8 条匹配报文（其中第二次 DNS UDP 未捕获到对应错误）：

| 捕获顺序 | 报文源 | 报文类型 | 外层 TTL | IPv4 ID |
| ---: | --- | --- | ---: | ---: |
| 1 | `1.1.1.2` | Echo Reply | 251 | **2144** |
| 2 | `10.0.2.10` | Echo Reply | 251 | **2145** |
| 3 | `10.0.2.10` | Type 3/3，引用 `1.1.1.2:53` | 250 | **17069** |
| 4 | `1.1.1.2` | Echo Reply | 251 | **2147** |
| 5 | `10.0.2.10` | Echo Reply | 251 | **2148** |
| 6 | `1.1.1.2` | Echo Reply | 251 | **2150** |
| 7 | `10.0.2.10` | Echo Reply | 251 | **2151** |
| 8 | `10.0.2.10` | Type 3/3，引用 `1.1.1.2:53` | 250 | **17076** |

Echo Reply 继续表现为两个源地址共享的递增 ID 序列，DNS 不可达报文虽然把源 IP 标记为 `10.0.2.10`，却使用另一组明显不同的 IP ID。

### B. 同轮加入 1.1.1.1 对照

`UTC=2026-11-19T09:05:13.8052491Z`，每轮先依次 Ping `1.1.1.2`、`10.0.2.10`、`1.1.1.1`，再向 `1.1.1.2:53`、`1.1.1.1:53` 发送 UDP DNS；重复三轮，取得全部 15 条匹配报文。

- `1.1.1.2` 与 `10.0.2.10` 的 Echo Reply：ID **2242、2243、2251、2252、2256、2257**（跨地址递增）。
- `10.0.2.10` 发出的三条、引用 `1.1.1.2:53` 的 Type 3/3：ID **17319、17325、17328**（另一序列）。
- `1.1.1.1` 的 Echo Reply 与同源、引用 `1.1.1.1:53` 的 Type 3/3：ID 按捕获顺序为 **41362、41373、41374、41375、41376、41379**。两种响应类型都落在这一个递增区间。

这使“仅因不同 ICMP 类型就必然使用不同 IP ID 计数器”这一简单解释不充分：在 `1.1.1.1` 的样本中，Echo 和 Port Unreachable 明显关联；在 `10.0.2.10` 的样本中则出现了分离的计数域。可能来自不同的生成路径、协议栈、虚拟设备或转发设备改写，但这只是候选机制。

### 综合解释与限制

**目前至少观察到两类互相关联的应答状态**：

1. `1.1.1.1` 与 `10.0.2.97`：Echo Reply、Type 3/3、Type 11/0 等多类 ICMP 共用或共同改写递增 IPv4 ID。
2. `1.1.1.2` 与 `10.0.2.10`：Echo Reply 共享递增 IPv4 ID，但 `10.0.2.10` 源的 DNS Type 3/3 另有独立的 IP ID 序列。

**这是报文生成/重写状态的关联证据，不是物理设备身份认证。** 单个物理设备可以拥有多种计数域或策略处理链；多个设备也可能共享计数器或由共同上游重写 IP ID。不同类型的 TTL 和长度可以支持区分处理机制，但无法凭空还原拓扑、NAT 层数、ACL 规则或真实运营设备型号。后续最有价值的是经授权的上游设备配置或交换机镜像口上的双向报文证据，不建议扩大未经授权的主机扫描。

全程仅发送低频、定向的已知目标请求，未更改网络设置或捕获并保存其他终端的数据。
